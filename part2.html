Element-Wise 逐元素算子 HIP + Triton

一道 Vector Add,看懂两种编程范式与"带宽受限"的真相。

🧩 本章精华(白话版)

判断标准与两种范式
逐元素 = 各干各的:算 C[i] 只需要 A[i]、B[i],位置之间零依赖 → GPU 上万个核心同时开工的天堂。

HIP:每个线程自己拼下标 idx = blockIdx.x×blockDim.x + threadIdx.x,一人一件,越界用 if (idx < size) 关门。
Triton:每个 program 拿一张任务单 pid×BLOCK + arange(0,BLOCK),整片装卸,越界用 mask 挡格子。
12B : 1 FLOP 与 6.95 倍
每个元素要搬 12 字节(读A 4 + 读B 4 + 写C 4)只换 1 次加法 → 带宽受限。

决定性实验:只改"同一轮 lane→地址的顺序",其余(线程数/寄存器/指令)全部相同——连续版 0.370 ms,跨步版 2.567 ms,差 6.95 倍。合并访存就是命门。
版本改动耗时有效带宽结论
hip-v0 / triton-t0一人一件 / 一单一片(均合并访存)0.336 ms≈599 GB/s打平,已顶到带宽
hip-v1 跨步只改地址顺序2.567 ms78.4 GB/s6.95 倍塌方 = 关键证据
hip-v2 / v3 / triton-t1grid-stride / float4 / BLOCK=10240.339-0.345 ms583-595 GB/s全部无效(负结果)
🗣️ 白话:螺丝厂
一个工人每拧 1 颗螺丝,要来回搬 12 斤货——产能卡在走廊和电梯,不在螺丝刀。所以"换大车(float4)""少雇人多跑趟(grid-stride)"都无用,只有让 32 人一队的取货路线连成片(合并访存)才有用。

Reduction 归约 HIP + Triton

把 1677 万个数加成一个数——当输出们开始"抢同一块地",协作与同步登场。

⚔️ 为什么会打架:数据竞争

所有线程同时对同一个地址做"读-加-写",后写的会覆盖先写的——像多人同时改文档同一行,互相覆盖。于是正确的最短写法是原子加:

最短正确版:全局原子加HIP
if (index < size) { atomicAdd(output, input[index]); }   // 所有人挤同一个窗口盖章

它正确,但所有线程竞争同一全局地址,实测 34.5 ms——不是"必然慢到不可用",但确实是本章的负基线。

🌳 树形归约:淘汰赛思维

▲ 8 个数的树形归约:log₂8 = 3 轮决出总和。淘汰赛打 7 场,但只需 3 轮决出冠军;串行循环赛则要排 7 轮。依赖深度从 O(N) 降到 O(log N),加法总数不变。
LDS + 屏障:block 内协作
每车间(block)先把货摆上共用餐车(LDS),两两合并,每轮后 __syncthreads() 等全班到齐;最后只派 thread 0 去总部原子加一次。全局 atomic 从"每元素一次"降到"每 block 一次"——4.33 ms。
Wave Shuffle:同排递纸条
wavefront 内 lane 本来就同进同出,__shfl_down 可直接读别的 lane 的寄存器——免写 LDS、免屏障。二阶段方案(各 block 交报表 → 第二个 kernel 汇总)进一步降到 0.051-0.060 ms。
⚠️ 本章的血泪坑
① __syncthreads() 放进 if 里会挂死——屏障必须在分支外,全班到齐才能进下一题。② FP32 加法不满足结合律:并行归约不能要求 bit 级等于串行结果,容差要提前约定。③ atomic 版每次启动前必须清零,否则第 k 次测量叠加前 k-1 次的结果。④ 普通 kernel 没有跨 block 的全局屏障——"dispatch 结束"就是同步边界,这是二阶段方案成立的原因。

Normalization:逐行 Softmax HIP + Triton

一行数据里,归约和逐元素轮流登场;真正的杀手不是性能,是 exp(1000)。

🌋 先救命,再谈快:指数溢出

不稳定版:直接 exp
输入 [1000, 1001, 1002]:exp(1000) ≈ 10434,远超 FP32 上限(≈3.4×10³⁸)→ 全变 inf → inf/inf = NaN。像温度计超出量程——读数报废,而不是"略有偏差"。
稳定版:先减行最大值
利用平移不变性(整行同减常数,结果不变):m = 行最大,x−m 后最大指数必为 exp(0)=1。
[1000,1001,1002]−1002 = [−2,−1,0] → 输出 [0.090, 0.245, 0.665] ✅

Softmax 的数据流是"两座归约的桥,架在一条逐元素的河上":max(归约) → exp(逐元素) → sum(归约) → 除(逐元素),行内共享分母、行间完全并行。

🚀 三种实现:从"三趟搬运"到"一气呵成"

实现思路耗时(4096×1024 FP32)
HIP 三 kernel 基线每阶段一个 kernel,中间张量 exp_tmp 写回显存;3 次 launch + 一次完整中间写读0.744 ms
HIP 融合 LDS 版一个 block 做一整行:LDS 树归约两次(max 与 sum),中间量全程不落显存;有意重算最后一次 exp 换取零中间存储0.116 ms
Triton 一行一 programload 时用 mask 补 -inf:max 不变、exp(-inf−m)=0 不污染分母——mask 同时是防越界和归约单位元0.038 ms
Triton t1(wide)更大 BLOCK + 更多 warps0.061 ms(反而慢,负结果)
⚠️ 本章负结果与误区
① t1-wide(更大 block+更多 warps)在主 shape 上更慢——"资源加大=更快"再次翻车。② 融合 ≠ "输入只读一次":融合版消除的是中间写回与多余 launch,不是必然的物理流量减半。③ 稳定公式不解决输入本身含 NaN/±inf 的情况。④ 融合版用的是整个 block 的 LDS 归约,别自称 "wavefront-level"。
11

GEMM:矩阵乘 HIP + Triton

算法天然自带数据复用——GEMM 优化的全部艺术,就是把这份复用真正落到 LDS 和寄存器上。

♻️ 复用从哪来?

C[i][j] = Σ A[i][k]·B[k][j]。A 的一行服务一整行输出,B 的一列服务一整列输出。朴素实现(一线程一输出)在源码层面要做约 2MNK 次 load;16×16 分块后,源码层 load 降到一半(128→64)——源码只暴露了复用机会,要靠 tile 把它变成物理现实。

LDS 分块核心:协作装货 + K 尾块填零HIP
tile_a[threadIdx.y][threadIdx.x] = row < M && a_col < K ? A[row*K + a_col] : 0.0f;  // 尾块填零
tile_b[threadIdx.y][threadIdx.x] = b_row < K && col < N ? B[b_row*N + col] : 0.0f;
__syncthreads();                      // 每个K tile 两次屏障:装完再算、读完再覆盖
accumulator += tile_a[ty][kk] * tile_b[kk][tx];   // 一份tile,全组16人分食
🗣️ 白话:食堂备菜
朴素版 = 每人炒菜前自己去仓库取一份食材(同样的菜被取了 16 遍)。分块版 = 先把一批食材整批端上共用案板(LDS),全组分食,吃完再进下一批。K 不是 16 的倍数?空位当 0 补齐(乘 0 不影响点积)。
⚠️ 高频 bug 与负结果
① B 的地址步长是 N 不是 K(inner 是 B 的行号,B 每行有 N 个元素)——最高频写错点。② 尾块不能让越界线程提前 return,否则 __syncthreads() 死锁。③ 实测:naive 0.400 ms → 分块版 0.183 ms(512³);Triton grouped 中心值 0.087 ms 但与基线的进程范围重叠,诚实记录为"不确定"。④ 不启用 autotune:其默认配置面向 A100/H100,消费卡 RDNA3 只有 64KB LDS。外部 tile 扫描:MoE 形状上最优/最差 tile 差 12.8 倍——tile 选择本身就是大江湖。
📐 用算术强度分区(第 7 章的地图派上大用场)
I = 2MNK ÷ 4(MK+NK+MN)。I<10 访存受限(LLM decode/MoE:要保占用率、保访存吞吐);I≥10 算力受限(prefill:专注寄存器复用与 LDS 吞吐)。先看这题是"搬砖累"还是"算得累",再定策略。

Fusion:单头 Attention 与在线 Softmax HIP + Triton

FlashAttention 思想入门:核心不是公式,是那个 S×S 中间矩阵"要不要写回显存"。

🎯 问题:S×S 长得比输入输出快得多

Scores = Q@Kᵀ/√D [S×S]→ P = softmax(Scores) [S×S]→ O = P@V [S×D]

Q/K/V/O 只有 S×D,而 Scores 和 P 是 S×S——序列一长,中间矩阵比主角长得还快。物化版(三 kernel、中间全写回显存)的好处是每一步可单独检查;融合版(在线 Softmax)让 S×S 全程不落地。

🔄 在线 Softmax:一本随时按汇率折算的账

逐块扫过 key,手里只维护三个状态:当前最大值 m、以 m 为基准的指数和 l、加权 V 累计 acc。每来一个新块:

在线 Softmax 递推(本章灵魂)text
new_m = max(m, x);  alpha = exp(m - new_m);  beta = exp(x - new_m)
l   = l * alpha + beta              // 旧指数和按新汇率折算,再加新账
acc = acc * alpha + beta * V[x]     // 旧加权累计同样折算
m   = new_m
🗣️ 白话:汇率折账
历史账本都是按"旧最大值"这个汇率记的;新最大值一来,旧账必须整体乘 exp(旧m−新m) 换算后再记新账。漏掉 alpha 重缩放是在线实现头号正确性错误。
实现(S=128, D=64 FP32)耗时说明
HIP 物化版(三 kernel)0.0586 ms每步可单独检查
HIP 在线版(教学实现)0.2274 ms反而慢!每个 key 一次 block 同步吃掉全部收益
Triton t0 / t1(BLOCK_K=16/32)0.0246 / 0.0174 msprogram 内维护状态,无 block 级同步
⚠️ 本章最重要的负结果
HIP 在线版输给了物化版——"消除 S×S 中间量"没有抵消"每个 key 一次同步 + 输出分子驻留 LDS"的代价。融合不是免费的午餐;真正的高性能实现(真 FlashAttention)要把 query/key 分块、状态进寄存器、用矩阵指令。本章结果只限此 shape,不外推。

结业实战:Fused RMSNorm HIP + Triton

一个算子集齐三种模式(逐元素平方 + 行归约 + 广播缩放),完整走一遍可复现优化闭环。

🧮 RMSNorm:只管音量,不管调零

Triton 版全文(一 program 一行)Python · Triton
values = tl.load(input_ptr + row*cols + offsets, mask=mask, other=0.0)
mean_square = tl.sum(values * values, axis=0) / cols      // 行归约:平方均值
inverse_rms = tl.rsqrt(mean_square + epsilon)              // 注意:epsilon 在开方内!
tl.store(output_ptr + row*cols + offsets,
         values * inverse_rms * weights, mask=mask)        // 广播缩放回整行

与 LayerNorm 的区别:不减均值(去掉 re-centering),只除以均方根(保留 re-scaling)。手算 x=[3,4]:平方均值 12.5 → RMS=√12.5 → 两个输出除以同一尺度。

实现(1024×4096 FP32)耗时点评
HIP serial(一线程一整行)1.505 ms行内零并行,明确的负基线
HIP block 协作版0.0584 ms约 26× 提升;平方与统计量全程不落显存
Triton t0 / t1(4/8 warps)0.0334 / 0.0301 ms同一数学 kernel,受控配置实验
⚠️ 别想当然的三件事
① "融合 = x 只读一次"不成立:HIP 版归约后要重读 x,Triton 看似只 load 一次但可能溢出到 scratch——要靠 profiling 说话。② 变慢的版本也要留档(某配置在 257 列有效、4096 列反而出 scratch)——它标出了资源边界。③ 误差阈值不能是万能常数:换 FP16/BF16 要按累加精度重定。
🎓 算子篇毕业:七步迁移法(走向独立优化新算子)
写数学语义和 reference → 标记模式组合(逐元素/归约/GEMM)与可融合边界 → 画数据生命周期 → 写最短正确基线 → 固定计时口径 → 每轮只改一项 → 用 profiling 而非 kernel 名字解释成败。这就是 Part 3 交给 Agent 自动执行的那套流程。
