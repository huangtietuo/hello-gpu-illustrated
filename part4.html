YOLO 部署 + Agent 自动优化 Alpha 骨架

把 Agent 的优化对象从单个算子升级为真实视觉模型——本章是路线图,数字待实测。

🗺️ 六步路线与能力边界

① 部署 YOLOv8(ONNX + MIGraphX / ORT-ROCm)→ ② 记录 baseline→ ③ Agent profiling→ ④ 出优化建议→ ⑤ 改配置跑对比→ ⑥ 优化报告
🧭 Agent 会做什么?瓶颈三分类
profiling 要回答:慢在预处理、NMS(筛重叠检测框),还是模型 kernel 本身?像排查快递慢:打包慢、分拣慢,还是路上慢?优化方向:batch size、精度、算子融合(小操作并大操作,减少往返)。
🚧 能力边界(最重要的一课)
Agent 能:profiling、改配置、换算子、出报告。
Agent 不能:自动写新算子并集成进 ONNX/MIGraphX。它是"会看报表调旋钮的助手",不是"会造发动机的工程师"。本章数据必须在基线平台实测后发布——未实测的数字一律不引用。
19

小模型 LLM 解码 + Agent 自动优化

16GB 显存约束下选 MoE 小模型(LFM2.5-8B-A1B 的 GGUF 量化版),llama.cpp ROCm 后端实测 decode 优化。

⚖️ prefill 与 decode:两种完全不同的动物

prefill(读你的 prompt)decode(一个字一个字往外蹦)
计算形态整段一起算,GEMM(矩阵×矩阵)每 token 一次,GEMV(矩阵×向量,M=1)
权重复用每个权重被大量 token 复用每个权重只用一次,读出即弃
瓶颈算力受限(可堆计算)带宽受限:吞吐上限 = 带宽 ÷ 每 token 读取量
白话全员开会,资料大家共用一对一答疑,每人都要翻一遍全部档案
🗣️ 白话:MoE 是"专员接待制"
LFM2.5-8B-A1B 总参数 8.47B,但每个 token 只激活 1 个专家——像一家 847 人的公司,每个客户只由 1 名专员接待。所以实际每 token 读取的权重远小于全量,这就是优化空间。原文实测反证:按全量 4.79 GiB 算理论上限 190 t/s,实测却到 214.6 t/s——反推需要 1.1 TB/s,超过 960 GB/s 物理带宽,证明稀疏激活真的在生效。

⏱️ decode 的一秒钟花在哪(时间预算)

权重 DRAM 读取 57%
反量化"格式税" 13%
attention/norm/launch/sync 30%

大头是"把权重从显存搬过来"(57%)。所以理论加速上限可算:就算把反量化成本降到零,Q8→Q4 也只有约 1.32×;算上 13% 格式税约 1.13×——与实测 1.12× 吻合。权重减半 ≠ 时间减半。

💥 本章高潮:"量化越低越快"被推翻

Q4_K_M(4.79 GiB)vs Q8_0(8.4 GiB),默认调度下 Q4 只快 11%。但把调度参数统一成 nw=1 后:

配置Q4_K_MQ8_0Q4/Q8
默认调度250.8 t/s225.4 t/s1.11×
nw=1(统一后)257.3 t/s345.5 t/s(+53.3%!)0.745×(Q8 反超!)
🔍 根因:不是量化的错,是调度的错
llama.cpp 某次更新后,Q4_K_M 进了 RDNA3 的 nw=1 白名单而 Q8_0 没有——默认调度对两种格式不公平。microbenchmark 显示 Q4_K 的 vec_dot 指令数是 Q8 的 10 倍但只慢 1.77×(dp4a 一周期可隐藏),真大头是内存:34B 跨两条 cache line。跨卡对照:NVIDIA 卡上 Q4 仍更快(1.148×/1.232×)——结论是"平台相关"的,不是普适真理。
🎓 全书收尾:三条边界与一个正确姿势
单卡三重边界:显存(fp16 的 8B 模型约 17GB 放不下,量化不是可选项)、生态(RDNA3 精度支持止步 GGUF/AWQ,vLLM 的 FP8/Marlin 全不可用)、Agent(只能做受控实验,纯 Agent 自动优化贡献≈0%)。PagedAttention、多卡、并发调度,留给下一本书 hello-mlsys。

而 Agent 的正确姿势,恰好是全书的落点:人给关键洞察,Agent 快速验证并留痕——benchmark 工具要支持"格式 × 调度参数"组合输入,按组合标注结论。前 18 章教的所有本事,最后都汇成这一句话。
