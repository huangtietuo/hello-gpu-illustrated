写给读者的话:这本书要带你去哪

不写代码的一章,但决定了你怎么读后面 19 章。

🗺️ 全书解决什么问题?

GPU 算子优化——让 GPU 上的计算跑得又对又快的整套工程能力。它串起算法、kernel 代码、访存模式和硬件资源。你可能问过这些问题:

  • 我的 kernel 到底慢在哪?
  • 瓶颈是访存还是计算?
  • 这个改动是真的变快了,还是测量在骗我?
  • 这套"测量→定位→修改→再测"的流程,能不能交给 Agent 自动跑?
🗣️ 白话:整车思维
判断一辆车为什么跑不快,不能只盯着发动机一个零件。GPU 优化也一样:kernel(发动机)、访存(油路)、硬件资源(底盘)是一个系统,本书教你的是"整车调校",不是"换个火花塞"。

🧭 三条主线(全书地图)

主线核心思想白话理解
Profiling-Driven先看数据再改代码,一切优化必须经 benchmark + profiling 验证先体检,后开药。过滤"看上去变快了"的伪优化
刷题导向每个算子走完 naive→优化的完整路径;顺序永远是:先正确性 → 再带宽 → 最后算术强度不做知识点串讲,做完整案例训练
Agent-Driven把优化闭环交给 Agent 自动跑;要记录失败尝试(失败记录比成功更值钱)不是"让大模型随便生成代码",而是给它尺子和裁判
理解硬件→ 学会 profiling→ 手写算子并优化→ 刷题攒方法论→ 交给 Agent 自动化
⚠️ 给初学者的最重要的警告
千万不要跳过第 1 篇(profiling,第 5-7 章)!测不准的时候,"优化"就是赌博。benchmark 数据的质量,决定你优化判断的上限。

🏥 第一次看懂 HIP 程序的"住院流程"

最小 HIP 程序的六个步骤,后面所有算子都是这个骨架,变的只是 kernel 内部:

① Host 备好数据→ ② hipMalloc 显存→ ③ H2D 拷入→ ④ 启动 Kernel→ ⑤ D2H 拷回→ ⑥ 检查+释放
🗣️ 白话:文员与车间
Host(CPU+内存)是文员:备料、发单、收货;Device(GPU+显存)是车间:只管加工。③⑤ 步是传送带(hipMemcpy),④ 步之后要 hipDeviceSynchronize 等车间干完——文员发完单不等于货做好了。
⚠️ 本章的坑
① ROCM_PATH 必须指向 _rocm_sdk_devel,指错成 core 会报 "cannot find ROCm device library"。② WSL2 里计算路径可用,但 rocm-smi/硬件计数器不可用,别当前提。③ 排错时只说"跑不通"最糟糕——要给机器信息、完整命令、期望与实际输出,用 2>&1 | tee xxx.log 留日志。

GPU 体系结构(上):线程怎么组织、怎么执行

跟着一次 kernel 提交,从软件分层一路走到硬件执行。

🚌 四层结构:从全厂到工位

软件层名字CUDA 叫法AMD 叫法白话理解
Gridgrid一次 dispatch这次任务的全体工人
Blockblockworkgroup车间:组内可协作、共用 LDS
—warpwavefront小队:硬件调度的最小单位,本机 32 人
Threadthreadwork-item / lane工人:一个逻辑编号,一份工作

全局工号公式(第 8 章还会重逢):tid = blockIdx.x * blockDim.x + threadIdx.x,配 if (tid < n) 越界保护。本机 256 线程的 block = 8 个 wave32 小队。

🗣️ 白话:大巴与一排座位
workgroup 是大巴上的全体乘客,wavefront 是一排座位(32 个)。硬件每次只对"一排"下达同一个动作——这一排就是执行的原子单位。

🎭 EXEC 掩码:分支发散的真相

同一排的 lane 走了不同的 if/else 分支怎么办?硬件的办法是用掩码轮流执行:保存掩码 → 让走 then 的 lane 执行(其他人失活)→ 反转掩码让走 else 的执行 → 恢复合流。

⚠️ 关键结论:不是两条路并行,是排队各走一遍
失活的 lane 不离场,只是原地待命。所以分支发散的代价是:整排的执行时间被最长的路径拖住。原文实测(16M 元素,受控实验):波前一致分支 0.237 ms,lane 级发散分支 0.245 ms,+3.33%——代价真实存在,但属于这个受控组合,不是"发散永远慢 3%"的通用罚单。
📌 软件分层 ≠ 硬件落点
LLVM 唯一保证的是:同一 workgroup 的所有 wavefront 一定落在同一个 WGP 上。其余(CU 怎么摆、哪个 SIMD 跑)取决于编译器,不能从源码反推。另外 multiProcessorCount=32 是诊断字段,≠ 物理的 64 个 CU,别混用名字。

GPU 体系结构(下):片上资源、数据通路与带宽

工人能同时接多少活、货走哪条路、路宽差多少倍——这一章回答三件事。

🏗️ 六层存储金字塔:越小越快,越大越远

寄存器 VGPR/SGPR · 工人手边桌面
LDS 128 KiB · 车间货架(workgroup 共享,显式管理)
L0 缓存(向量 32K / 标量 16K) · 硬件自动管
L2 8 MiB + Infinity Cache 64 MiB
GDDR6 16 GB · 约 640 GB/s · 远处总仓
🎯 占用率:能同时塞多少活
一个 wavefront 等显存回话时,硬件切给别的 wavefront 干活(延迟隐藏)。能同时驻留多少 wavefront,由 VGPR / SGPR / LDS 谁先用光决定,而不是线程数。比喻:产线数量受"最先耗尽的资源"限制——工具柜、图纸柜、工作台,哪个满了都上不了新人。⚠️ 占用率也不是越高越好:硬压寄存器会逼出溢出(spill),反而更慢。
⚠️ 三个最常踩的概念坑
① LDS 不是缓存——它是你显式分配、自己摆货的货架;缓存才是系统自动管的。② 逻辑字节 ≠ 物理流量——按算法算的读写量,和真实 DRAM 事务量是两回事(缓存可能命中)。③ 规格容量 ≠ 性能——"有 128 KiB LDS"不等于"用满就快"。

🚗 三组实测:路宽差多少倍?

① 合并访存(读全局内存)
相邻 lane 读相邻地址 = 一卡车拉一排货架;stride-257 打散后,带宽从 571 GB/s 掉到 71 GB/s(约 1/8)。这就是第 8 章 6.95 倍实验的理论地基。
② LDS bank 冲突
LDS 内部有多个可并行的"收银台"(bank)。stride-32 让 32 人挤同一台 → 42.2 ms;stride-33 错开一台 → 8.09 ms,回到基线。排队还是分流,就差一个错位。
③ WMMA:矩阵专用快车道
整条 wave32 协作调用一条矩阵乘加指令,合力算一块 16×16×16(FP16 输入/FP32 累加)。教学微基准里 2.30× 于普通 VALU 循环(2.08 vs 0.90 TFLOPS)。比喻:32 人从"各算各的"变成"流水线分工"。代价:布局是芯片定死的,而且它远非 rocBLAS 的理论峰值。
📋 结论三分法(原文的治学态度)
可迁移:边界正确性优先、逻辑与物理指标分离。需重测:stride、LDS 布局、资源占用、分支代价——换卡换形状要重新量。仅 gfx12:WMMA intrinsic 是本代专属。

第一个程序 + 第一次性能分析

跑通手写 vector add,并第一次回答:"我离硬件极限有多远?"

📏 第一把尺子:算术强度与带宽利用率

📐 算术强度 AI
AI = 计算量 ÷ 搬运量。vector add 每元素:读 a 4B + 读 b 4B + 写 c 4B = 12 字节,只做 1 次加法 → AI ≈ 0.083 FLOP/Byte。搬得多、算得少 → 必然卡在"腿"(访存)而不是"脑"(计算)。
📊 带宽利用率
实测(N=16.7M,warmup 5 + repeat 30,GPU event 计时):GPU median 0.347 ms,有效带宽 583 GB/s。利用率 = 583 ÷ 640 ≈ 91% → 访存效率已经到位,想再快只能提高算术强度(融合算子)。
🗣️ 白话:GPU 比 CPU 快 21 倍?
实测 GPU 0.347 ms vs CPU 8.54 ms ≈ 21 倍——但这是"数据已在显存、只量 kernel"的口径。算上 Host↔Device 搬运,差距小得多;数据再小,CPU 反超。正确问法是算总账:kernel 执行 + 数据搬运 + 启动开销,值不值?

⏱️ 计时四件套(第一次登场)

benchmark_vector_add.py 核心Python
start.record(); c = a + b; end.record()   # 在 GPU 时间线打两个点
torch.cuda.synchronize()                  # 等 GPU 真干完
times.append(start.elapsed_time(end))     # 取两点间隔(ms)
# warmup 5 次甩掉冷启动 → 正式 repeat 30 次 → 用 min 估带宽
⚠️ dispatch 开销:什么时候不能忽略?
发射一个 kernel 要走:host API → 内核驱动 → 写 AQL 包 → 敲门铃 → GPU 调度,实测约 2.6 μs。本章 kernel 0.345 ms,启动占比不到 1%,可忽略。但如果把任务拆成成百上千个小 kernel(后面的 split-KV 案例),启动开销就能吃掉全部收益。
✅ 本章验收 + 试一试
vector_add 输出 status: PASS, max_error: 0;benchmark 输出 PASS。试一试:把 --size 改成 1<<20 和 1<<26 各跑一次,先猜带宽是单调变化还是先升后降——建立"规模 vs 性能"的第一感觉。记得写实验记录:目标→流程→结论,不留记录,三天后等于白做。
