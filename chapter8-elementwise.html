逐元素算子是什么?——"各干各的活"

判断标准只有一句话:算输出 C[i],只需要看输入同位置的 A[i] 和 B[i]。

🎯 一眼判断法

拿到任何算子,先问一个问题:

🗣️ 白话判断标准
"算输出第 i 个位置,我需要跟别的位置商量吗?"
不需要,各算各的 → 逐元素算子(Element-Wise),GPU 最喜欢。
需要开会(求和、求最大)→ 不是逐元素,那是后面章节的主角。

最典型的例子就是本章主角 Vector Add:C[i] = A[i] + B[i]。第 0 号位置的结果只跟 A[0]、B[0] 有关,跟 A[5]、B[99] 毫无关系——所以 所有位置可以同时、独立地开工,这正是 GPU 成千上万个小核心最擅长的事。

点"播放",看 A、B 的每一列怎么独立地汇成 C 的同一列。任何一列出问题,其他列完全不受影响。

👪 逐元素算子家族

同一套路换个公式,就是另一个算子。这一章的所有结论,对整个家族通用:

算子公式白话理解
Add / Sub / Mul / DivC[i] = A[i] ±×÷ B[i]两排队伍一一配对合并
ReLUC[i] = max(A[i], 0)负数全部清零,正数放行
Scale & BiasC[i] = a·A[i] + b每件货统一放大再贴标签
Clamp(限幅)C[i] = min(max(A[i], lo), hi)把越界的数夹回安全区间
🚫 这些不是逐元素(当心!)
求和 reduce:C = A[0]+A[1]+…+A[n],输出只有一个数,要"全班一起算",位置之间有依赖。
Softmax:每个输出都要先知道"这一行的最大值",得先开会、再干活。
它们会在后面章节登场,手法完全不同。
🗣️ 白话:为什么 GPU 喜欢"各干各的"
一条流水线上,如果每个工位的产品互不影响,那就可以雇一万个工人同时开工,人越多越快。反过来,如果每个环节都要等其他人的结果(像求和那样一层层汇报),人再多也快不起来——GPU 的并行优势,正是建立在"逐元素这种无依赖的活"之上的。

两种写法:HIP"一人一件" vs Triton"一组一片"

同一道题,两种世界观。先看全景,后面两节各走一条路。

🗺️ 全景对比(下面画的是 N=6 的小例子,实际启动覆盖到 0–7)

HIP / CUDA 范式

一个人,一件货

每个线程像单件工人,只拿着一个标量下标 i,自己去 A、B 各取一件,加完放回 C 的 i 号位。程序眼里只有"我"。

T4干 4
T5干 5
T6没事做

一个组长,一整片货

每个 program 像小组长,拿一张任务单(offsets),上面写着"你负责 4、5、6、7 这一片",整片一起装进寄存器算。程序眼里有"一块"。

HIP 的 blockDim.x = "每个车间雇多少工人";Triton 的 BLOCK_SIZE = "每张任务单写多少个格子"。名字里都有 block,但完全不是一回事——本章实测里,256 个线程/块 和 1024 格/单 是两种不同维度的选择。

📌 怎么选?

本章两条路都走一遍,最后用同一把尺子(带宽)量出真相。

先定规矩:C[i] = A[i] + B[i] 的数学与裁判

优化之前,先把"什么叫做对了"钉死。否则快了 10 倍,算错了,一切白搭。

✍️ 三条固定语义(一道题的"题干")

项目本章的约定
数学定义C[i] = A[i] + B[i],i ∈ [0, N),N = 16,777,216(2²⁴,约 1677 万个元素)
数值类型FP32,float,连续存放在显存,不搞特殊布局
判定标准和 PyTorch 参考实现逐元素对比,最大绝对误差 max_abs_error = 0.0 才算通过

为什么要固定 FP32?因为加法本身在不同精度下可能得到不同结果。类型一变,"谁对谁错"就没法裁判了——所以先把类型钉死,后面所有版本都在同一张考卷上答题。

🧮 手算 5 秒,建立直觉

举例(N=4)
A = [2, −1, 4, 3]   B = [7, 3, −1, 2]
C[0]=2+7=9  C[1]=−1+3=2  C[2]=4+(−1)=3  C[3]=3+2=5
→ C = [9, 2, 3, 5]

本章所有 7 个版本(4 个 HIP + 2 个 Triton + PyTorch 参考),都要先过这一关。

👨‍⚖️ 自动裁判:pre-check → 跑 kernel → post-check

裁判流程固定三步:先检查输入是否符合预填数据 → 执行 kernel → 再检查输出与 PyTorch 的结果是否逐元素一致。两头一夹,谁也蒙混不过。

为什么故意选一个"怪长度"?N = 1027

N=1027 不是 256 的整数倍。启动 5 个车间、每车间 256 工人 = 1280 个线程,前 1027 个有活干,后面 253 个线程空转。这逼着每个版本都要回答同一个问题:"多出来的那批人,你打算怎么管?"

🗣️ 白话
就像 1027 个乘客上大巴,一辆坐 256 人,得开 5 辆车——第 5 辆只坐了 3 个人,剩下 253 个座位空着。空座不是 bug,但要保证没人坐错位置、也没人被落下。后面的 mask 和 if,干的就是这个事。

瓶颈在哪?12 字节搬运 vs 1 次加法

这是本章最重要的一页"账本"——先算账,再动手,猜出瓶颈,再用实验验证。

🧾 算一笔账

每算一个元素,显存里要发生什么、计算单元要干什么?

动作去哪搬多少
读 A[i]显存 → 计算单元4 字节(FP32)
读 B[i]显存 → 计算单元4 字节
写 C[i]计算单元 → 显存4 字节
合计—12 字节,只换来 1 次浮点加法(1 FLOP)

这有点反直觉——你以为 GPU 在拼命"算",其实绝大多数时间在"搬"。1 次加法对 12 字节搬运,吞吐上限被搬运一侧卡死。

🗣️ 白话:螺丝厂
一个工人每拧 1 颗螺丝(计算),就要去仓库取 2 个零件、送回 1 个成品(访存),来回要搬 12 斤。螺丝刀再快也没用——工厂的产能卡在走廊和电梯上,而不是螺丝刀上。这类"搬运为主、计算为辅"的活,叫访存受限 / 带宽受限(memory-bound)。
📐 记两个数就够
算术强度 = 计算量 ÷ 访存量 = 1 FLOP ÷ 12 B ≈ 0.083 FLOP/Byte。这个数越小,越说明是"搬运型"任务。
由此可得实验里最常用的尺子:有效带宽 = 12 × N ÷ 耗时。版本跑得越快,这个数越接近显存的搬运极限,说明你把"走廊"用满了。
🧪 科学态度:这只是假设
"12B : 1FLOP ⇒ 带宽受限"目前只是从数据量推出的假设。它成立吗?要等 ⑤⑥⑦ 节的实测数据来检验——而且你会发现,唯一一个"假设成立"的强证据,恰恰来自那个最慢的版本(2.57 ms 的跨步版)。

HIP 四级台阶:v0 → v1 → v2 → v3

HIP 是 AMD GPU 上的底层编程接口(和 NVIDIA 的 CUDA 一个地位)。这条路上,每个数字都由你亲手拼出来。

🧱 动手前,先认识 4 个对象

组织结构(从大到小)
Grid(全厂) ← 由若干 Block(车间) 组成 ← 每个车间若干 Thread(工人)。
每个工人手里有一块小小的私有寄存器,车间里有一块公共的共享内存(LDS)。
Wavefront(小队)
硬件真正调度的单位:32 个工人一组,同进同出。一个车间 256 人 = 8 支小队。后面"合并访存"的秘密,全在小队身上。
🔢 本章实测的数字锚定(N = 2²⁴)
N = 16,777,216 个元素;每车间 blockDim.x = 256 人 → 需要 grid = 65,536 个车间(65,536 × 256 = 16,777,216,刚好铺满)。
下标公式:index = blockIdx.x × blockDim.x + threadIdx.x
白话:你的全局工号 = 你在第几个车间 × 每车间人数 + 你是车间里第几号。

🪜 v0:一个线程,一个元素

最直白的写法:启动 1677 万个工人,每人只负责一个下标。

hip_vector_add_v0.hipHIP · C++
__global__ void vector_add(const float* A, const float* B, float* C, size_t size) {
  size_t index = blockIdx.x * blockDim.x + threadIdx.x;  // 我的全局工号
  if (index < size) {                                    // 多出来的人,收工
    C[index] = A[index] + B[index];                      // 干自己的那一件
  }
}

🧮 公式拆解 + 小计算器

把三个数代进去玩玩,感受"工号是怎么拼出来的"。第三个下拉框专门模拟 N=1027 时"多出来的工人"。

🚗 顺带认识"访存合并 Coalescing"

概念预告(下一级台阶的主角)
小队(32 人)同一步要取的 32 个地址,如果正好挤在同一小段连续显存里,硬件可以像"一卡车拉走一整排货架"那样合并成很少几次大搬运——这叫合并访存。v0 里相邻线程的地址正好相邻(工号 0,1,2,3…),天然合并,这就是它不慢的原因。

🪜 v1:一次改变世界的"地址顺序"实验 ⭐ 本章核心

一个大胆的问题:如果每个工人干的活不变,只改变"谁负责哪个下标"的顺序,耗时会变吗?

🧪 受控实验设计(控制变量,只动一处)
只启动 1 支小队(32 线程),每人往返 32 趟(每趟管 1 个元素)。同一个下标集合 0–1023,两种排列:
① 连续版:index = base + r × 32 + lane —— 第 r 趟,0 号工人管第 r×32 个,1 号管下一个……
② 跨步版:index = base + lane × 32 + r —— 0 号工人从头到尾管 0,32,64,…,1 号管 1,33,65,……
除此之外什么都不变:同样的线程数、同样的 VGPR/SGPR 寄存器、同样的指令数(编译 trace 逐项相同)。

▶️ 动画:同一轮里,两种顺序的"取货路线"(8 人小队示意,每人 4 趟)

货架按 32 字节一组分区(8 个 FP32 = 一组,开一次门)。小队每轮 8 人同时伸手——数一数每轮要开几扇门?

连续版
跨步版
点"播放":逐轮点亮每个工人(lane)实际触碰的元素。
📊 实测结果(RX 9070 XT)
连续版 0.3696 ms(544.7 GB/s) vs 跨步版 2.5672 ms(78.4 GB/s)——6.95 倍的差距!而两版的编译 trace(线程数、寄存器、指令)完全一致。
白话:两支队伍搬一样多的货,唯一区别是取货路线。连续队一次拉满一车;跨步队每轮都绕 4 个货架各拿一点,卡车永远装不满。
⚖️ 这一节教会我们的方法论
控制变量 + 时间差同时出现,才敢说因果。6.95 倍的耗时差,和"唯一变量=地址顺序"绑在一起,才能断定:合并访存就是这类算子的命门。这也是全章成本模型假设最硬的一块证据。

🪜 v2:Grid-Stride——少雇点人,每人多跑几趟

v0 需要 65,536 个车间才能铺满 1677 万元素。另一种思路:只开少量车间,让每个工人来回跑很多趟。

hip_vector_add_v2.hip(核心循环)HIP · C++
__global__ void vector_add_grid_stride(float* A, float* B, float* C, size_t n) {
  size_t index  = blockIdx.x * blockDim.x + threadIdx.x;   // 工号
  size_t stride = gridDim.x * blockDim.x;                  // 全体工人的总数 = 一趟的步长
  for (size_t i = index; i < n; i += stride) {             // 跑完一趟,跨一整步再来
    C[i] = A[i] + B[i];
  }
}
步长是什么?
全厂一共 stride 个工人。0 号工人干完 i=0,下一趟跳去干 i=stride,再下一趟 i=2×stride……
只要步长 = 工人总数,所有工人拼起来恰好无缝覆盖全部下标,不多不少。
grid 开多大?默认 CU × 8
本章默认 grid = 计算单元(CU)数 × 8。直觉:每个 CU 是一个"食堂",×8 是给调度器留的余量,让每个 CU 手里始终有活排队。
📊 实测:0.3435 ms —— 和 v0 的 0.3363 ms 基本打平
对这类"逐元素"任务,只要访存模式保持合并,v0 那种"人海战术"和 v2 这种"少人多趟"没有本质区别。Grid-Stride 的真正价值在后面章节(比如配合共享内存的算子)才会显现,这里先当"认识它"。

🪜 v3:float4——一次搬 4 个 + 尾部处理

既然瓶颈在搬运,那就把手推车换大:让每个工人一次操作 4 个连续的 float,挤成一个 float4 类型(4×4=16 字节)。

📦 N=18 时的分组示意

🟩 4 组 float4(0–15)由向量化主干处理;🟨 剩下 16、17 两个"散货"走标量尾部。注意 8–11 这组虽然凑齐 4 个,但起始地址 8×4=32 字节,恰好对齐,没问题——对齐检查看的是起始地址是不是 16 字节的整数倍。
hip_vector_add_v3.hip(主干)HIP · C++
__global__ void vector_add_float4(float* A, float* B, float* C, size_t n) {
  size_t v4      = n / 4;                    // 能凑成几整组 float4
  size_t tail    = n % 4;                    // 剩下几个散货
  size_t nvec    = v4 * 4;                   // 向量化主干管到的边界

  const float4* A4 = reinterpret_cast<const float4*>(A);  // 把 float 数组"看成"float4 数组
  const float4* B4 = reinterpret_cast<const float4*>(B);
  float4*       C4 = reinterpret_cast<float4*>(C);

  size_t i = blockIdx.x * blockDim.x + threadIdx.x;
  size_t stride = gridDim.x * blockDim.x;
  for (size_t k = i; k < v4; k += stride) {          // 主干:一次一整车
    float4 a = A4[k], b = B4[k];
    C4[k] = make_float4(a.x + b.x, a.y + b.y, a.z + b.z, a.w + b.w);
  }
  size_t base = i;                                    // 尾部:前 4 个工人各领一件散货
  if (base < tail)  C[nvec + base] = A[nvec + base] + B[nvec + base];
}
⚠️ 三个最容易搞混的事实
① reinterpret_cast 不搬数据——它只换一副"眼镜",告诉编译器:请把这段内存按 float4 的格式重新解读,数据一个字节都没动。
② 一次 float4 load ≠ 一次访存指令——硬件可能把它拆成多条访存指令,所以"源码里写 4 个"不等于"显存里 1 次事务",向量化收益要看硬件实际怎么发指令。
③ 对齐检查看的是"起始地址"而不是"数组够不够 4 个"——起始地址必须是 16 字节(4×float)的整数倍,凑齐 4 个元素但起始地址歪了,照样不能安全地按 float4 读。
📊 实测:0.3452 ms —— 没有变快
为什么?因为 v0/v2 里相邻线程的地址本来就连成一片,硬件早就把访存合并得很好了;再换大车,走廊还是那条走廊。"向量化"不是万金油,合并访存才是本命。这个"没变快"本身,就是一个有价值的负结果(见 ⑧ 节)。
🪜 HIP 台阶小结:每一级只动了一处
v0 打地基:一人一件 + 合并访存。v1 只改"谁负责哪个下标" → 6.95 倍差距,合并访存实锤。
v2 改组织方式(grid 大小 + 每人工作量) → 打平。v3 换数据类型(float4 + 尾部) → 打平。
一步步做实验,每一步只有一个变量——这就是性能工程的基本功。

Triton 两条路:七行代码 + 一个参数

Triton 是 OpenAI 出的 Python 算子语言:你描述"一片怎么算",寄存器分配、向量化这些脏活它替你干。

🐍 kernel 正文:真的只有 7 行

triton_vector_add.pyPython · Triton
@triton.jit
def add_kernel(x_ptr, y_ptr, out_ptr, n_elements, BLOCK_SIZE: tl.constexpr):
    pid = tl.program_id(0)                                   # 我是几号小组长
    offsets = pid * BLOCK_SIZE + tl.arange(0, BLOCK_SIZE)      # 我这张任务单:一整排下标
    mask = offsets < n_elements                               # 单子上哪些格子真的存在
    x = tl.load(x_ptr + offsets, mask=mask)                    # 按单子整片装货(挡住越界)
    y = tl.load(y_ptr + offsets, mask=mask)
    tl.store(out_ptr + offsets, x + y, mask=mask)              # 整片写回
🧩 逐行白话
pid:组长编号(相当于 HIP 的 blockIdx)。
offsets:注意!它不是单个整数,是一整排数——像"任务单"。
mask:布尔排,哪些格子真实存在。
tl.load / tl.store:按任务单整片装卸,越界格子被 mask 挡住,不会出错。
🏠 宿主(host)代码:Python 一侧
grid = (triton.cdiv(n, BLOCK_SIZE),)          # 需要几个小组长 = 向上取整
add_kernel[grid](a, b, out, n,
                 BLOCK_SIZE=256, num_warps=4)
cdiv(n, BLOCK) = (n + BLOCK − 1) // BLOCK,N=1027、BLOCK=256 时 = 5 个组长,和 HIP 的 5 个车间一个道理。特别提示:在 ROCm 上跑,照常写 torch.cuda 即可,ROCm 会翻译成 HIP。

🎬 可视化:N=13,BLOCK_SIZE=8,mask 在干什么

这正是官方 Triton-viz 工具展示的例子。点下面的按钮切换小组长,看"任务单"上哪些格子放行(绿)、哪些被 mask 拦下(灰)。

🗣️ 白话:mask 就是"关门"
任务单是按固定大小(8 格)印的,N=13 凑不满最后一张单。后 3 个格子指向不存在的 A[13..15]——硬件不可能真的去读,所以编译器让这些格子整个通道失效,像商场关门那样,谁也进不去。对比 HIP:那边是给每个线程发"if 不通过就收工"的指令,这边是"任务单上直接划掉",思路不同,目的一样。

🔑 三句解读

负结果的价值 · 迁移 · 总结 · 小测验

"试了但没用"的实验,和"成功了"的实验一样值钱——前提是记录下来。

🗂️ 本章的四张"负结果"卡

❌ 跨步版慢 6.95 倍

只改地址顺序,耗时 0.37 → 2.57 ms。负结果反手变成了最重要的正面证据:合并访存就是命门。

❌ Grid-Stride 没有更快

0.3435 vs 0.3363 ms,基本打平。教训:对纯逐元素任务,"少人多趟"不省时间;它的用武之地在别的算子。

❌ float4 没有更快

0.3452 ms。教训:源码向量化 ≠ 实际提速;访存已合并时,换大车只添麻烦(还要处理尾部)。

❌ BLOCK_SIZE 调到 1024 没有更快

0.3385 ms,VGPR 反而从 8 涨到 24。教训:调参要看瓶颈在哪——瓶颈在带宽时,加大 tile 只多占寄存器。

📌 负结果的适用边界
这些"没用"只是在"逐元素 + 合并访存 + 这块卡"的条件下没用。换一个算子(比如需要数据复用的卷积)、换一块卡(寄存器更紧张),同样的技巧可能立刻见效。做实验,永远把条件一起记录。

🚚 学会就迁移:这套打法直接抄到别的算子

ReLU
把"读 B"整个砍掉,只读 A:C[i] = max(A[i], 0)。访存量 12B → 8B,账本更倾斜于搬运,套路不变:保证 A 的访问连续。
Scale & Bias
C[i] = a·A[i] + b:只有 A 是数组,B 换成两个标量参数(不占 4B/元素的搬运),访存 12B → 8B。架构完全照抄 Vector Add。
🔥 进阶:算子融合(Fusion)
既然瓶颈是"把数据从显存搬来搬去",最狠的优化就是少搬几趟:把 add 和 relu 融合进一个 kernel,先加完立刻判 max,中间结果留在寄存器里,不给它回显存的机会——省下一次完整的"写 C 再读 C"。

🧠 记忆卡片(考前速记)

1 · 判断逐元素 = 各干各的算 C[i] 只需 A[i]、B[i],无依赖 → GPU 并行的天堂。求和/softmax 要"开会",不是逐元素。
2 · 范式HIP 想下标,Triton 想任务单blockIdx·threadIdx 拼出一个标量 vs pid×BLOCK+arange 得到一排下标;if 关门 vs mask 挡格子。
3 · 账本12B : 1 FLOP4+4+4 字节换 1 次加法,算术强度 ≈0.083 → 访存受限。有效带宽 = 12N ÷ 耗时。
4 · 命门合并访存同一轮 32 个地址挤在同一小段连续显存,才能"一卡车拉满"。6.95 倍的实验证明它是唯一命门。
5 · 边界怪长度 N=1027多出来的线程/格子要管好:HIP 用 if(size),Triton 用 mask。谁也不能读越界、谁也不能被落下。
6 · 方法控制变量 + 记录负结果每次只改一处;trace 相同才有因果;"没变快"也是数据,标注适用条件后它就是别人的路标。

📝 小测验(点开看答案)

Q1:为什么说 Vector Add 几乎注定是"带宽受限"?
每个元素要搬 12 字节(读 A 4B + 读 B 4B + 写 C 4B),却只产生 1 次加法。算术强度 1/12 ≈ 0.083 FLOP/Byte,远低于 GPU 的平衡点,所以吞吐上限卡在显存带宽上——后来的 6.95 倍实验和 598 GB/s 的实测都印证了这一点。
Q2:v1 实验里,连续版和跨步版的唯一区别是什么?为什么这样设计?
唯一区别是同一轮内 lane→地址的排列(index = base + r×32 + lane vs base + lane×32 + r)。线程数、寄存器、指令数(编译 trace)完全相同。只有把其他变量全部钉死,6.95 倍的时间差才能干净地归因给"地址顺序→合并访存"这一个因素。
Q3:N=13、BLOCK_SIZE=8 时,第二个 program 的 mask 会拦下哪些格子?
offsets = 1×8 + [0..7] = [8..15];mask = offsets < 13,所以 8–12 放行(5 个),13、14、15 被拦下(3 个)。cdiv(13,8)=2 个 program,正好覆盖全部 13 个真实元素。
Q4:hip-v3 的 float4 没有变快,这算失败吗?说明了什么?
不算失败,是一个有价值的负结果:它说明在访存已经合并、瓶颈已顶到带宽上限时,"源码级向量化"带不来额外收益(硬件可能本就把相邻 float 的访存合并成大事务)。同时提醒:reinterpret_cast 不搬数据、float4 load 可能拆成多条指令、对齐看起始地址。
