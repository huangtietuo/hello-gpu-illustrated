Agent 篇:让 AI 替你跑优化闭环

把前两部分教给人类的方法论——可信计时、Roofline、单变量实验、留痕记录——封装成 Agent 可调用的工具,让大模型在"带尺子的考场"里自动优化 kernel。四章递进:Agent 是什么 → 工具怎么封装 → 循环怎么组装 → 实战跑通 2.19 倍。

Agent = LLM + 工具 + 循环 ReAct + Reflection 权威工具 vs 自由工具 配对裁决晋升制 Radeon 8060S 实测 0.705→0.322 ms
💡 本篇一句话:LLM 负责理解和提议,代码负责相信什么——性能数字只认工具返回,晋升只认 accept_candidate 的配对证据。

Agent 入门:最简模型与游戏规则

Agent = 大模型(决策)+ 工具(行动)+ 循环(观察→再决策),直到收敛或触达步数上限。

🔁 ReAct + Reflection:想一步,做一步,看一步

🧠 LLM 决策(Reason)→ 🔧 调工具(Act)→ 👁 观察结果(Observe)→ 💭 反思策略(Reflect)→ 🧠 下一轮决策… ↺ 循环往复,直到"不再调工具"或步数上限 max_steps
主循环骨架(教学版,刻意一眼看完)Python
for step in range(1, max_steps + 1):
    message = llm.chat(history, tools=schema)   # Reason:决定要不要调工具
    if not message.tool_calls:                  # 不再行动 → 尝试收尾
        return message.content
    for call in message.tool_calls:             # Act:编译/计时/画像/晋升…
        observation = executor.call(...)         # 工具回传结构化观察
        history.append(observation)              # 观察回灌,进入下一轮
🗣️ 白话:指挥官与侦察兵
LLM 是只动嘴的指挥官;工具是执行并回传实测数据的侦察兵;循环是作战例会——每轮看侦察报告再下指令,而不是听指挥官拍脑袋宣布"我军大胜"。

⚖️ 权威工具 vs 自由工具:法庭只认证物

🏛️ 权威工具(结果即事实)
compile_kernel · bench_kernel · profile_kernel · accept_candidate · measure_peak。性能数字只认它们,晋升由 accept_candidate 单独完成。
💬 自由工具(允许发挥)
ask_user · convert_kernel · run_code · read_reference。可以出主意、查资料,但它们的"自测加速比"不许写进报告。
🎯 为什么算子优化特别适合 Agent?
三个"Agent 友好"特征,恰好对应闭环的三个环:目标可量化(延迟中位数、配对改进比例、距峰值空间)、行动可封装(五个标准工具)、反馈可验证(PyTorch reference 当标准答案 + warmup/GPU event/中位数计时)。一句话:有标准答案、有标准动作、有标准判卷的科目,才好自动化。
15

工具封装:给 Agent 一张格式统一的体检报告单

把人类的计时习惯、正确性检查和 profiling 直觉,收编成 Agent 可调用、返回可解析的标准化工具。

🧰 工具三件套 + 唯一晋升入口

工具回答什么问题返回什么(节选)白话
compile_kernel能不能编译?{"ok":false,"stage":"compile","errors":[{"line":42,"msg":"expected a type"}]}错误按行列出,不是泼一盆日志
bench_kernel有多快?median 0.322 ms · p95 0.340 · 带宽 156.2 GB/s秒表:只报成绩,不判名次
profile_kernel慢在哪?bottleneck "DRAM bandwidth" · memory-bound · AI 0.167要瓶颈信号,不要几千行 trace
measure_peak极限在哪?带宽 210.5 GB/s · fp16 27.8 TFLOPS(实测缓存)量"这条路的限高架",禁止写死型号常数
accept_candidate能不能晋升?{"accepted":true,"improvementFraction":0.0150}唯一有钥匙的面试官,落选记录也存档
🗣️ 白话:晋升答辩制
候选方案要和现任 incumbent交错配对计时:中位改进 ≥1% 且多数配对为正,才能覆盖 best.py;无论成败都追加进 trajectory.jsonl 轨迹。落选者自动离场,擂主不变——回退不是 undo 按钮,是晋升制的副产品。
⚠️ 设计红线
① Agent 拼不好 shell 字符串——必须结构化接口。② 错误按行列出,文本模型会被噪音日志淹没。③ "工具失败不算任务失败"——结构化错误回灌对话历史,触发反思重试。④ 反馈要分层:编译成败、正确性、性能三层信息互相独立,Agent 才知道卡在哪层。

算子优化 Agent 设计:六步主循环

流水线工人(工具)按标准检测,设计师(LLM)只能提案,盖章权在质检章。

🔄 六步闭环

① 读题建合同→ ② LLM 生成候选→ ③ compile→ ④ bench→ ⑤ profile→ ⑥ accept? 接受 → 更新 best.py | 拒绝 → 读错因、换机制 → 回到 ②;直到收尾 → 中文报告 + 确定性汇总
📜 读题 = 签工程合同
把规格变成可检查的条件:reference、atol/rtol、入口签名;把性能目标变成可量化的数字:改进阈值或绝对延迟。开工前双方都认账。
🎛️ 一次只改一个机制
第一版唯一目标是正确(它是一切比较的基线);之后每轮根据 profile 与优化模式手册,一次改一个主要机制——控制变量法,Agent 也要遵守。
🩺 反思三层次:看化验单三连问
现象(数字多少、差目标多少)→ 原因(profiling 说什么:访存受限/占用不足/启动开销)→ 行动(下一步改什么、预期是什么)。映射到工具反馈:读 errors[] 修语法;读 below_threshold 换方向;memory-bound 就减搬运/减启动,compute-bound 就减运算。
⚠️ 本章负结果:R5 的教训
Agent 把 block_size 推到 8192:编译通过、正确性通过,但中位延迟大幅变慢(-17.3%)——过大 block 伤害占用与调度。评测器拒绝后,Agent 回到 4096 路线。会承认方向走不通,是闭环成熟的表现。

多轮优化实战:0.705 → 0.322 ms 的完整账本

vector_add 上 10 轮全自动优化:5 次接受、5 次拒绝、一次有价值的失败——证明的是闭环可信,不是极限加速。

🧾 怎么读这份账本

📈 成绩与归因
0.705 → 0.322 ms ≈ 2.19×(延迟降 54%)。来源全部可追溯:block 256→4096(grid 启动次数约减 16 倍)+ num_warps 提到 32。每一步都是工具账本说了算,不是模型口头宣布。
🚧 诚实边界(不可外推)
2.19× 发生在"baseline 故意朴素"的前提下;vector_add 本就近带宽墙。"3-5×"的承诺只针对有真实优化空间的算子(融合 softmax、naive reduction/matmul)。纯 Agent 发明新结构的能力≈0——正确打开方式是"人给关键洞察,Agent 快速验证并留痕"。
🗣️ 白话:实验记录本
工作区固定五件套:任务合同 task.json、参考答案 reference.py、现任擂主 best.py、硬件档案 hardware.json、逐轮账本 trajectory.jsonl。失败页码也装订进册——报告里"事实"与"推测"严格分栏,像论文的数据区与猜想区。
