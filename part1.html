5

benchmark 与可信计时:你测的数字凭什么信?

性能优化不从改代码开始,从把时间量准开始。

🔥 四个"无聊"细节,决定数字可不可信

细节为什么必须做白话理解
Warmup(热身,约5-20次)首轮含一次性开销:JIT 编译、缓存冷启动、GPU 时钟爬频运动员上场要热身,第一套动作慢不是水平问题
Repeat(重复,几十到几百次)单次结果只是偶然:后台任务、调度抖动都会让数字漂移量血压要多量几次看中位数,不能一锤定音
Synchronize(同步)CPU 发命令就返回了,不等 GPU 干完;不同步量到的是"提交耗时"time.time() 是"下单时间",GPU event 才是"包裹在途时间"
GPU Event 计时在设备时间线上打两个点取间隔,精度够量 μs 级 kernel给 GPU 的工作本身打卡,而不是给办公室的门打卡
可信计时骨架(PyTorch)Python
for _ in range(warmup):            # ① 热身,甩掉编译/缓存/爬频
    op(x)
torch.cuda.synchronize()
for i in range(repeats):          # ② 正式计时 N 次
    start[i].record(); op(x); end[i].record()
torch.cuda.synchronize()          # ③ 等 GPU 全部干完
times = [s.elapsed_time(e) for s, e in zip(start, end)]  # ④ 汇总 median/min/p95
🗣️ 白话:统计量各有分工
mean 容易被几个"异常慢"拖累;median 代表大多数情况;min 最像"没被任何干扰"的一次,常用来估带宽上限;p95/std 看波动。报数字至少带上 median 和 min。

🧪 两个经典骗局,本章现场拆穿

骗局一:缓存伪提升
第二次跑同一份输入明显变快?那只是数据被 L2"捂热"了,不是代码变好。输入刚好塞进缓存时数字会"异常好看"——所以要换多个 size 看趋势。"我什么都没改它就快了"= 背过原题的模拟考。
骗局二:fp16 时间减半 = 快一倍?
实测 4096²:fp32 0.337 ms(601 GB/s),fp16 0.173 ms(587 GB/s)。时间确实约一半,但带宽几乎没变——省的是字节数(fp16 每数 2 字节),不是搬运效率。口径不同,结论完全不同。

📏 用 footprint 扫描,画出缓存层级

只跑一个规模永远看不见缓存。按工作集大小分级测 copy 带宽(一读一写):

工作集8 MiB64 MiB256 MiB
有效带宽785.1 GB/s(踩中 L2!)572.8 GB/s568.6 GB/s

8 MiB 的"高分"是 L2 命中的红利;64 MiB 之后 ~570 GB/s 才是 GDDR6 的真实水平。比喻:用大小不同的行李去试电梯,才能画出"客梯/货梯"两层结构。

✅ 本章验收:十条检查清单
固定规模 · 固定 dtype · 区分初始化与正式计时 · warmup · repeat · synchronize · 计时器选对(禁用 time.time() 量 μs kernel)· 锁时钟/排后台 · 记录环境 · 一次只改一个变量。
6

用 rocprof 找到慢在哪里:一个 6.7 倍的悬案

两个 vector add 差 6.7 倍——bench 确认差距,rocprofv3 定位慢点,但先别急着下结论。

🔎 悬案:linecross 版慢了 6.7 倍

linecross(本章自造的对照名):每个 lane 负责 stride 个连续元素,相邻 lane 的起点隔开 stride×4 字节。stride=32 时,同一排 32 个 lane 要的地址分散在 32 段不同的地方——合并访存彻底泡汤。

实现耗时有效带宽慢多少
coalesced(连续版)0.334 ms603 GB/s—
linecross stride=10.336 ms599 GB/s≈1.0×
linecross stride=322.25 ms89.7 GB/s≈6.7×
🗣️ 白话:收作业
连续版像全班按学号连坐,老师一趟收齐;linecross stride=32 像每人只收"隔 32 排"的座位——跑动距离和趟数全变了。

🎫 rocprofv3:给每个 kernel 打上下班卡

采集 kernel 级 tracebash
rocprofv3 --kernel-trace -o logs/kt.csv -f csv -- \
    ./vector_add_bench --kernel linecross --size 16777216 --block 256 --stride 32 \
    --warmup 5 --repeat 10

CSV 里每个 dispatch 一行:关键列 Kernel_Name、起止时间戳(纳秒)、Grid_Size、VGPR/SGPR。它把"程序慢"缩小成"哪个 kernel 慢、慢在哪一栏"。

kernel单次最短Grid SizeVGPR
coalesced329 μs16,777,2168
linecross(s32)2202 μs524,288(1/32)16
⚠️ 反直觉:还不能急着归因!
stride=32 的 6.7 倍不能全记在"合并访存"头上——它同时改了三件事:①地址排布 ②每线程循环次数 ③Grid Size。有效带宽 603→89.7 只是同一份时间换了个单位,不算第二份独立证据。stride 扫描(stride 1→256,耗时 0.34→25.3 ms)展示的是"组合效果"。profiler 帮你找慢点,不自动替你证明原因。
✅ 本章行动项
设计公平对照:固定线程总数与每线程工作量,只改索引公式(连续版 i = base + j×32 + lane,分散版 i = base + lane×32 + j)——这正是第 8 章 v1 实验要做的事,两章在这里握手。
7

读懂 Roofline 图:一张地图决定优化方向

把时间、数据量、硬件上限放到同一张图上,一眼看出该往哪使劲。

⛰️ 什么是 Roofline?

横轴是算术强度 AI = 计算量 ÷ 搬运量(FLOP/Byte),纵轴是实际性能(FLOPS),两张对数轴。硬件有两条"天花板":带宽斜线(搬运极限)和算力水平线(计算极限),交点叫拐点。工作点落在拐点左边 → 访存受限,优化方向是"少搬/复用/融合";落在右边 → 算力受限,方向是"少算/降精度/上矩阵指令"。

▲ 第6章两个实现的 Roofline(数据来自原文):横轴位置相同(AI 都是 0.083),纵轴却差 6.7 倍——AI 相同不代表表现相同,合并访存决定了你"贴不贴得上屋顶"。
🗣️ 白话:高速公路地图
两条天花板是"限速线",你的 kernel 是"车"。看图三连问:①车在地图哪一侧?(该省油还是该换引擎)②车速多高?③离头顶的天花板还差多少?——差距最大的那条,就是值得发力的方向。

🧾 三个公式 + 一页记录

三个换算口径text
算术强度  AI = F / B          # F=计算量(数操作数), B=搬运量(dtype×元素数)
实际性能  P  = F / t          # t 来自第5章的 GPU event 实测
有效带宽  BW = B / t          # 与参考线比较用,注意口径(见下)
⚠️ 有效带宽 603 > 参考线 510 GB/s,是超光速了吗?
不是。有效带宽统计的是算法有效字节,工作集可能被缓存接住、写路径也可能不走 DRAM。它适合比较两个实现,不能当真实 DRAM 流量。比喻:按"净货重"算的效率超过了公路限速——只是口径不同,不是超能力。
工作点位置含义下一步排查
AI 小,贴着斜线典型访存受限减访存 / 融合算子 / 提高数据复用
AI 小,离斜线远访存效率不高查地址连续性(合并访存)、多余读写
AI 大,贴着水平线典型算力受限WMMA / 降精度 / 减少计算
离两条线都远没吃到任何上限查 launch 开销、同步、输入规模太小
